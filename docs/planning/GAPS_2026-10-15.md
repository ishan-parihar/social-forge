## 2. Phase 6 bulk — dual auth ports (L each; sources are sibling dirs)

> **2026-10-15 REVISION — P6.1–P6.3 REJECTED on evidence, not effort.**
> Reading the port sources before porting changed the plan:
>
> - `linkedin-lyr/voyager_auth.py` documents (issue #2601, proven live,
>   2026-09-08) that replaying browser-minted LinkedIn cookies over plain
>   HTTP — from ANY egress — is itself a **session-revocation trigger**: the
>   first HTTP probe answered 302 + `li_at=delete me` + `clearSiteData`, and
>   the revocation propagated into the source browser. Their own messaging /
>   search / feed tools therefore run through the **browser extractor**
>   (Obscura DOM), not Voyager HTTP; only the profile-edit path touches
>   Voyager endpoints, still inside the browser context.
> - `facebook-lyr` and `instagram-lyr` are the same architecture
>   (`drivers/browser.py`, browser-context scraping clients) — the same
>   design decision by the same author, for the same reason.
>
> social-forge's stack is plain reqwest/wreq. A "port" onto it would not be
> a port of these tools at all — it would be the naive plain-HTTP variant
> the sources deliberately do not ship, with a demonstrated
> session-killing outcome. Building it would be shipping a landmine as a
> feature.
>
> **The safe dual-auth surface is what social-forge already has**: X
> (GraphQL over plain HTTP works — twitter-lyr is itself an HTTP CLI),
> Reddit www+modhash (HTTP, works), Telegram user (grammers MTProto — a
> native protocol, not web-replay), WhatsApp web (wa-rs, native), Skool
> (extension cookie). For LinkedIn/Facebook/Instagram cookie-side
> operations, the browser-context tools in the sibling lyr projects are
> the right tool — the integration story is using them alongside
> social-forge, not re-implementing them worse.
>
> What REMAINS actionable from this section: P6.4 (Telegram parity — port
> from tg-cli, native-protocol, safe) and P6.5 (Reddit parity — HTTP,
> safe).

Design constraint (already landed, `954ea77`): dispatch inside the provider
via `integrations.auth_method`; **never** register `linkedin-cookie` etc. as
separate providers.
