## 1. Verdict

The architecture is sound: a single binary, SQLite, an in-process scheduler, a claim-by-state-flip, an outbox, a circuit breaker and a pending-post lifecycle. Most of the remaining risk comes from **two parallel publish pipelines and per-tool ad-hoc provider construction**.

These are where the defects cluster:

- Fixes have landed in one path but not the other. Example: the G-01 empty-id guard exists only in `PostService`.
- Several Tier-1 publish paths are broken right now. All of these are silent until a post is due:
  - X media upload;
  - LinkedIn (version sunset);
  - TikTok (endpoints);
  - Instagram/Facebook/LinkedIn first-comment;
  - Reddit OAuth refresh;
  - multi-platform threads.

The agent-facing surface also has three structural blockers:

1. `social-forge mcp` cannot run while the systemd `serve` daemon runs.
2. The agent skill teaches a `mcp-call` command that does not exist.
3. Per-platform MCP tools cannot pick an account.

**P1 correctness.**

**[C] Shutdown sleeps a fixed 30s** (`main.rs:424`) instead of draining. Runtime drop kills publishes that are still running. Await the scheduler's JoinSet with a deadline and set `TimeoutStopSec` above it.

**[C] The circuit breaker and semaphore are per provider, not per account** (`registry.rs`). One revoked X account opens the breaker for every X account.

**[C] 401/403 from X GraphQL maps to `TokenExpired`** (`x.rs:392`). The scheduler then "refreshes" a cookie session, which is impossible. Error 226 ("automated") is shown as an expired token.

**[C] X GraphQL `queryId`s are hard-coded** (`x.rs:36-56`). `twitter-lyr` re-discovers them from the JS bundles; social-forge breaks every time X rotates them.

**[V] Meta Graph versions are mixed**: v19.0 ×2, v21.0 ×20, v22.0 ×1. v19 is past its 2-year window and v21 is at the edge of its window. Use one `const GRAPH_VERSION`.

**[V] Medium's public API no longer issues integration tokens**, so the API path only works for legacy tokens.

**[C] An Instagram/Facebook "refresh" returns `Err`.** Integrations with `token_expires_at` set fail `resolve_token` at day 60. Page tokens derived from long-lived user tokens don't expire, so store `expires_at = NULL` for them.

## 4. Redundancy & fragmentation (the root cause of most P0s)

1. **Two publish pipelines.**

   `scheduler::publish_post` (`scheduler/mod.rs:780-1235`) and `PostService::publish` (`services/posts.rs:249-440`) each carry their own copies of:
   - token resolve;
   - thread linking;
   - first comment;
   - the encryption-downgrade code.

   `PostService` lacks the `post_pending` lifecycle, the semaphore and the breaker. The scheduler lacks the empty-id guard.

   → Extract one `services::publish::publish_one(db, registry, post, opts)`. The scheduler, REST "publish now", MCP and CLI all call it.

2. **Platform MCP tools bypass the pipeline.**

   `x_create_tweet`, `li_create_post`, `th_create_thread`, `tt_*`, `pi_*`, `sk_*`, `sl_*`, `md_*`, `dv_*`, `hn_*` and `wp_*` call `provider.publish()` directly. That means:
   - no `posts` row;
   - no idempotency;
   - no rate limit;
   - no breaker;
   - no analytics link.

   `x_create_tweet` also hard-codes `mime_type: "image/jpeg"` (`tools_x.rs:611`), so video breaks.

   → Make every `*_create_*` tool a thin wrapper over `publish_one` with `state=published-now`.

3. **Per-call provider construction.** There are 28 `Provider::new` calls in `tools_google.rs` alone, and 87 HTTP-client constructions in 49 files. `XProvider::new` builds a BoringSSL `wreq` client **and reads browser cookie DBs** on every MCP call, with a panicking `.expect` (`x.rs:121`).

   → Providers come only from `ProviderRegistry`. Per-account credentials are passed as arguments, never set by mutating a shared provider (`prepare_from_token` / `set_cookie_credentials` are `&mut self`, which is why tools clone fresh ones). Use one shared `reqwest::Client` plus one shared `wreq::Client`.

4. **Google implemented twice.** `google.rs` re-implements Gmail, Calendar and Drive alongside `gmail.rs`, `calendar.rs` and `drive.rs`. Google OAuth refresh exists ×6 (AST-identical). → Keep one module per API and one `google_oauth::refresh()`.

5. **Cookie extraction ×3.** `x_cookies.rs` and `reddit_cookies.rs` each re-declare `home_dir`/`chrome_default_profile`, although `browser_cookies.rs` exists for this. → Use one extractor parameterised by `(host, names)`.

6. **Two thread creators.** `create_thread_posts` (with group) and the staging loop (no group). → Use one (B4).

7. **Config reads scattered.** There are 25 `std::env::var` reads outside `config.rs` (APP_URL, STRIP_LINKS_FROM_X, DUB_CO_*, PROVIDER_CONCURRENCY_*, …). `scheduler/mod.rs:787` re-reads `APP_URL` on every publish. → Move them into `Config`.

8. **Error types.**
   - 97 `Result<_, String>`.
   - 11 `Box<dyn Error>` (the scheduler).
   - 23 production `unwrap`/`expect`.
   - 3 `#[allow]`.

   Per the skill (ch. 4): use a `thiserror` `PublishError { Provider(ProviderError), Db(sqlx::Error), Validation(String) }` for the publish path and keep `anyhow` in `main`/CLI only. Use `#[expect(clippy::too_many_arguments)]` with a reason (ch. 2).

## 5. Agent-first gaps (the product objective)

### 5.1 MCP ↔ daemon conflict [C] — highest leverage

`social-forge mcp` boots the **full server**: the writer lock, the HTTP port 6543, all 6 pollers, and Telegram/WhatsApp clients (`main.rs:127`, `:392`). With the systemd `serve` running, the agent's MCP process exits on the lock. Without systemd, each agent session runs its own scheduler.

**Fix (pick one, both are small):**

- **(a) Thin `mcp`.** When the lock is held, open the pool read-write with **no** pollers, no HTTP, no lock, and no messaging clients. SQLite WAL handles the short writes, and the daemon's scheduler picks up the rows. This costs about 15 MB RSS per agent instead of a full server.
- **(b) Expose MCP on the daemon.** Add rmcp streamable-HTTP at `POST /mcp` behind the existing auth, so agents connect by URL with zero processes spawned.

Recommend **(a)**, plus (b) later for remote agents.

### 5.2 Seamless multi-platform staging

```jsonc
// posts_stage / `social-forge stage --json @file`
{
  "content": "base copy",
  "integrations": ["x", "linkedin-page:acme", "reddit"],  // id, provider, or provider:name
  "overrides": {
    "x":      { "content": "short copy", "thread": true },
    "reddit": { "settings": { "subreddit": "rust", "title": "…" } },
    "youtube":{ "settings": { "title": "…", "privacy": "public" } }
  },
  "media": [{ "url": "…" }],
  "schedule": "2026-10-20T09:00:00+05:30",
  "first_comment": "…",
  "dry_run": true            // returns per-platform readiness, writes nothing
}
```

- Returns one `group_id`. Every lifecycle verb (`reschedule`, `unschedule`, `publish-now`, `delete`, `status`) accepts that `group_id`, so one campaign is one handle.
- Readiness **errors** (missing subreddit, zero content limit, disconnected integration, `refresh_needed`) reject that integration. Warnings stay non-blocking.
- MCP parity is missing for REST routes that already exist: `/api/posts/thread`, `/unschedule`, `/{id}/date` (move group), `/group/{id}`, `/validate`, and campaigns. Add these as `posts_thread`, `posts_unschedule`, `posts_reschedule`, `posts_group`, `posts_validate`.

### 5.3 The agent skill documents a command that doesn't exist [C]

`skills/social-forge-agent/SKILL.md` (×6), `references/providers.md` (×14) and `quick-reference.md` (×116) tell agents to run `social-forge mcp-call <tool> --args '<json>'`. There is no such subcommand in `cli/mod.rs`. Instagram posting is documented only through it.

→ Implement `mcp-call`: construct `SocialForgeMcpServer` in-process and dispatch by name. That is about 40 lines with rmcp's `call_tool`, and it makes every MCP tool shell-callable.

### 5.4 No account selection on platform tools [C]

Only 6 of ~250 platform tool inputs take an `integration_id`; the rest pick the first integration. This defeats the "agency managing many accounts" objective.

→ Add `integration: Option<String>` (UUID or `provider:name`) to the shared input base and resolve it through one helper.

### 5.5 Tool-surface cost [C]

All 329 tool schemas are advertised on every session, with no filtering. For an agent-first and low-resource goal, add `SOCIAL_FORGE_TOOLSETS=core,x,reddit` (default `core` ≈ 25 tools) and two meta-tools, `tools_search(query)` and `tools_enable(set)`. This drops tens of thousands of prompt tokens per agent session.

## 6. Scheduler / systemd

What works: the `queued→publishing` claim in one `BEGIN IMMEDIATE`, boot and per-tick reclaim, the posting-gap alerts, and the outbox drain. Gaps:

| Gap | Fix |
|---|---|
| Ticks are serialized on the slowest publish (JoinSet awaited in-tick). A 3.5-min IG/X video finalize delays **every** other due post. | Don't await publishes in the tick. Spawn them into a long-lived JoinSet owned by the scheduler task, and gate per integration with the semaphore. Only finalize (polling) holds the permit. |
| 30s poll granularity, and a new "publish in 1 min" waits up to 30s. | Add a `tokio::sync::Notify` poked by create/schedule. Sleep until `min(next_scheduled_at, 30s)`. |
| No liveness signal: a panicked scheduler task leaves `/health` green. | Write a `last_tick_at` atomic and have `/ready` return 503 if it is older than 3 ticks. Optionally use `sd_notify` `WATCHDOG=1` (`Type=notify`, `WatchdogSec=120`). |
| The unit is system-wide and needs sudo. It has no hardening and no `TimeoutStopSec`. | Add `social-forge service install [--user]`: a user unit plus `loginctl enable-linger`. Add `NoNewPrivileges`, `ProtectSystem=strict`, `ReadWritePaths=<data>`, `PrivateTmp`, `TimeoutStopSec=60`. |
| Reclaim threshold is 300s, which is shorter than the worst legitimate publish (IG reel finalize 200s + retries + backoff). | Make it 900s, or refresh `updated_at` while finalizing. |
| A failed thread head still lets later parts go out standalone. | Block the rest of the group: set later parts to `error` with "predecessor failed". |

## 8. Essentials missing (filtered for a single-user, agent-run agency; Postiz-only/team features excluded)

1. **Media transform pipeline.** Aspect-ratio crop/pad (IG 4:5–1.91:1, Reels/TikTok/Shorts 9:16), resize, and video transcode/trim via an optional `ffmpeg` binary. This is the #1 cause of real-world publish failures. There is no `ffmpeg` or image handling today.
2. **Delete or edit a *published* post through one verb.** The trait has neither (only platform-specific tools). Add `delete_published` and an optional `edit_published` to `SocialProvider`.
3. **UTM auto-tagging per platform/campaign.** None today; it pairs with the existing Dub short-links.
4. **Unified inbox.** Comments, DMs and mentions across providers in one list with a single `reply` verb. The pieces exist per provider but aren't aggregated.
5. **Per-integration posting slots / queue.** "Next free slot for this account" exists as `find_slot`; the next step is making stage accept `schedule: "next-slot"`.
6. **Best-time-to-post** from the stored engagement history.
7. **WhatsApp Cloud API**, **Discord webhook posting** (no bot needed), and **Telegram channel targets** discovery for the bot.
8. **Platforms:** no additions recommended. The won't-port list in `tier.rs` is right. Effort is better spent on cookie variants (§3) than on new networks.
