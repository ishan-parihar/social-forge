## 2. Failures — mistakes I made

### 2.1 Tool misuse: `edit` in symbol mode, four times in a row

I called `edit` with `symbol: "x"` four separate times, each rejected with
`edit: symbol mode requires both 'symbol' and 'content' string properties`. I then
"switched" to a bash/python heredoc — but called `edit` with symbol again twice more
before actually abandoning it.

**Cost:** ~6 wasted calls, and it seeded a habit of reaching for `python3` heredocs
through bash for ordinary file edits, which then caused failures 2.2 and 2.3.

**Rule:** symbol mode is *only* `{symbol, content}`. A partial edit is `{edits:[...]}`.
Neither takes `symbol`. Pick one mode and stop.

### 2.2 Using `python3` heredocs for edits the `edit` tool should do

Because 2.1 wore me down, I wrote several edits as `python3 - <<'PY'` scripts over
bash. Two of them failed on `assert old in s` because my assumed text didn't match the
file (`block`, `login block`, `context block`). One wrote nothing and reported success
via `print` before the assert — I initially misread which of my two replacements had
landed.

**Rule:** multi-edit is what `edit({edits:[...]})` exists for. If a heredoc's `assert`
fires, the file is untouched — re-read before retrying.

## 3. Failures — subagent management

### 3.1 Malformed first `task` spawn

My first `task` call had a truncated JSON payload (`tasks[0].task` cut mid-sentence,
invalid JSON). The tool spawned an agent named `BuildActivityLog` with a broken task

**Rule:** these payloads are long. Compose them fully before sending; a truncation
silently produces a confused agent, not an error.

`BuildResearchSurface` returned a body containing `[TABLE ROW LIMIT: 10 of 45 rows shown]

artifact, not a real status. I correctly distrusted it and verified from disk — but I had
already spent a turn writing a corrective message to the agent based on its claims.

**Rule:** subagent prose is untrusted. `git status`, file existence, and a compile are
the only acceptance evidence.

### 3.3 Not owning the integration seam

I ran `cargo clippy` while both subagents were mid-edit and hit errors in *their*
in-flight files (`ExternalWordGap` not found, then a missing lifetime). I fixed one of
them directly (the lifetime on `str_at`) while the other agent was still writing, which
risked conflicting writes.

**Rule:** clippy/test against a tree with live agents is measuring a moving target.
Stash or wait for them to land, then run the gate once. Fixing another agent's
half-written file is how you get a duplicate fix or a clobber.

### 3.4 Delegating without an explicit "don't run the gate" boundary in one spawn

Both tasks said to run svelte-check and clippy themselves. With two agents and me all
compiling in one workspace, cargo's build lock serialised everything and I got
`Blocking waiting for file lock on build directory` noise in `err.log`.

**Rule:** exactly one owner runs the gate. Children report what they changed; the
integrator verifies.

### 3.5 Leaving a stray artifact

`err.log` was written at the repo root by the subagent and left behind. I removed it
after noticing.

**Rule:** name the scratch path in the task context so agents write outside the repo.

## 4. Failures — correctness in code I shipped

### 4.1 The probe's theme switch was untracked — produced 48 bogus FAILs

My first probe toggled `documentElement.classList` directly. The app's `theme.init()`
(onMount, `+layout.svelte:120`) reverts it from localStorage, which defaults to `dark`.
Result: the page sat with **no theme class at all**, CSS custom properties resolved to
nothing, and the probe reported e.g. a 14px calendar `h1` at **1.27:1** and 18px glyphs
at 1.32:1. I spent several turns chasing these as real defects.

I proved them false only after dumping the live `getComputedStyle` chain with a
standalone script, which showed the h1 at a healthy `rgb(30,41,59)`.

**Root cause:** I changed app state without going through the app's own state channel.

**Fix:** `context.addInitScript` seeds `localStorage['social-forge-theme']` before any
page script runs, so `theme.init()` reads the right value.

**Rule:** when driving an app from outside, set state through the app's own mechanism
(localStorage / its API), never by poking the DOM it owns.

### 4.2 Login failed with 403 because no Origin was sent

`page.request.post` sends no `Origin`. The CSRF middleware requires one matching
`FRONTEND_URL`. The probe died with `Login failed: HTTP 403`.

**Rule:** read the middleware before scripting against a gated endpoint.

### 4.3 `providerInk` first implementation was wrong twice

- **Attempt 1 — asymmetric ratio.** `(surfaceL + 0.05) / (inkL + 0.05)`. Against a dark
  surface this *falls* as the ink lightens, so the search inverted and 25/26 providers
  collapsed to pure white. Verified only because I ran the helper standalone over the
  whole palette instead of eyeballing it.
- **Attempt 2 — ignoring the second surface.** Required 4.5:1 on white only, which
  silently fails the dark theme.
- **Attempt 3 — collapsed to black.** Required 4.5:1 on *both* surfaces with one static
  hex. Impossible: `#ffffff` is 1.0 and `#131720` is 0.007 in relative luminance, and
  every mid-tone hue fails one of them. 25/26 → `#000000`, destroying channel identity.

**Correct shape:** the fix is theme-aware — `inkForSurface(hex, surface)` with the
symmetric ratio `(max+0.05)/(min+0.05)`, lighten on the dark card, darken on the light
card. Final: 26/26 pass on both themes, worst 4.52:1, 0 degenerate, hue preserved.

**Rule:** a colour-contrast helper must be exercised against *every* input in *every*
theme before it ships. One example proves nothing.

### 4.4 Deleted two helpers in one block replace

When I replaced the `providerInk` doc block, my slice boundary ate `hexLuminance` and
`shiftLightness` too. `svelte-check` caught both. I restored them one at a time across
two more turns.

**Rule:** after a block replace in a file with private helpers, grep the helper list
before re-running the type-check.

### 4.5 The probe's overlap check has a parent/child false positive (FIXED)

48 FAILs remained, all `overlap`, and reading `CalendarHeader.svelte` shows the cause:
`<button …><span aria-hidden="true">{v.icon}</span> {v.label}</button>` — the reported
pairs are an ancestor's box against its descendant's ("📅 Day" vs "📅", "Today's
Schedule" vs "(Asia/Calcutta)"). A child is *always* inside its parent's rect, so these
are geometric tautologies, not layout defects.

**Fix applied:** skip pairs where one element contains the other
(`a.contains(b) || b.contains(a)`), and require both boxes to have their own text.
That left 4 hits, all of the same shape (a button's own emoji glyph against the
button's label) — the button's own text node and its icon span are siblings, so
containment does not apply. They are the same class of tautology and were left as
advisory noise.

**Rule:** a geometric detector must exclude the containment relation before calling
overlap a defect. "Box A intersects box B" is only meaningful for independent boxes.

## 5. Failures — verification process

### 5.1 Ran the gate against a stale build

The probe measured an old frontend: the server was serving the embedded assets while
`vite build` wrote to `frontend/build`. I only found this by tracing `ServeDir` /
`FRONTEND_DIR` in `src/api/mod.rs:719-731`, then restarted with `FRONTEND_DIR` pointed
at the fresh build.

**Rule:** before measuring a web surface, prove which bytes the server is serving.

### 5.2 Used the operator-shaped `.env` for the smoke server

I copied the repo `.env` into a scratch dir and only then noticed `APP_PASSWORD` was
unset (the only match was `BLUESKY_APP_PASSWORD`) and had to inject a throwaway.

**Rule:** build the smoke env explicitly; never assume a copied env is complete.

### 5.3 Polled a background task with `bash_status`

I called `bash_status` in a loop on long runs instead of `bash_watch` / `wait`. Each
poll was a wasted turn. One `bash_watch` call also failed on
`timeoutMs must be between 1 and 120000`.

**Rule:** `bash_watch(pattern)` or end the turn and let the completion reminder wake me.
`bash_status` is a one-shot, never a loop.

### 5.4 `cargo test` output parsed with fragile awk

My first two summaries reported `passed=0 failed=0` because the awk field indices were
wrong. A small python parse gave the truth (`720 passed, 0 failed`).

**Rule:** parse structured output with a real parser, and sanity-check that the total
is non-zero before believing it.

### 5.5 Let a "gate green" be inferred rather than measured

I nearly wrote up `cargo test` as passing from a truncated tail. The full result had
3 failing targets (`--lib`, `activity_feed_test`, `research_aggregate_test`) that only
appeared by summing every `test result:` line.

**Rule:** "exit 0" from the shell and "all tests passed" are different claims. Sum them.

## 7. Carry-forward checklist for the next session

1. **Before any delegated work:** enumerate the exact file list each agent may touch,
   forbid the gate, name a scratch path outside the repo.
2. **Before any gate run:** confirm no subagent is mid-write; run the gate once, as the
   single owner.
3. **Before measuring a web page:** prove the server's asset source (`FRONTEND_DIR`),
   build fresh, restart; set state (theme, auth, onboarding) through the app's own
   channel, never by DOM poking.
4. **Before shipping a colour/geometry helper:** run it over every input in every theme,
   and exclude containment from any overlap test.
5. **Every `test result:` line, summed** — never a tail, never an awk guess.
6. **Subagent output is untrusted** until `git status` + a compile agree with it.
7. **One mode per `edit` call:** `{edits}` for partial, `{symbol, content}` for whole
   symbol. Never `symbol` without `content`.
8. **`ctx_reduce` immediately**, one output at a time, when its content is in reasoning.
9. **A geometric/colour detector's FAIL is a hypothesis**, not a verdict — reproduce it
   against the real computed style before changing app code.

### 8.1 The `live_*` test binaries hit the real APIs, and they are flaky

`cargo test` runs `tests/live_x_test.rs` (and the other `live_*` binaries) against the
REAL X/Reddit/Discord/... APIs using the operator's cookies in `.env`. They are not
`#[ignore]`d, so a full `cargo test` includes them.

Observed 2026-10-19: `live_x_test` failed in 2 of 4 full runs, with
`X whoami HTTP 429 Too Many Requests` and `client error (SendRequest)` on
`UserByScreenName`. Twelve consecutive `cargo test --lib` runs were clean, and the
failure is always in the live binary, never in an offline one.

**The documented gate (AGENTS.md §4.1) is `cargo test --lib`, not `cargo test`** - the
live binaries are outside it. Treat a red `live_*` binary as an environmental signal
(the operator's cookies are rate-limited), not as a regression in the code under test.
To verify an offline change, run the specific offline binaries:

```
cargo test --lib
cargo test --test uuid_filter_test --test analytics_engagement_test ...
```

**Rule:** a flaky test is a defect until proven environmental. Prove it by showing the
failure is in a live-API binary and by re-running the offline gate several times.

### 9.1 DMs EOF error — FIXED

`GET /api/dms/conversations?integration_id=<X>` returned
`{"error":"error decoding response body: EOF while parsing a value at line 1 column 0","code":"provider"}`.

Root cause: `src/social/x.rs` `v2_get`, `v2_post`, `v1_get_with_cookies` call
`resp.json().await` unconditionally. X answers HTTP 200 with an empty body for
empty DM conversation lists, so `serde_json` fails with EOF → `ProviderError::Api`
→ HTTP 502 → frontend `"Invalid JSON response"`.

Fix: added `read_json()` helper that reads body as text and treats empty/whitespace
as `json!({})`; all four HTTP methods now route through it. Rebuilt, restarted,
live endpoint now returns a meaningful provider error instead of EOF (verified live).
CLIPPY clean after the edit.
